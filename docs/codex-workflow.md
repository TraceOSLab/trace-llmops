# Codex 协作方式

## 可以直接问吗？

可以。以后在这个仓库中打开 Codex 后，可以直接描述问题，不需要每次重新介绍技术栈和目录。根目录 `AGENTS.md` 提供项目级背景，进入 `llmops-api/` 时，更近的 `llmops-api/AGENTS.md` 会补充后端规则。

`AGENTS.md` 不是万能知识库。它负责告诉 Codex“去哪里看、默认如何协作、哪些事情不能做”；具体架构和运行方式由 `docs/` 保存，代码仍然是最终事实来源。

## 本项目的默认协作模式

- 你负责手写和理解核心代码；
- Codex 默认负责阅读调用链、解释设计、定位异常、审查代码和给出局部示例；
- 普通提问默认只读，不修改文件；
- 只有你明确说“帮我实现”“修改这个文件”“按方案执行”时，Codex 才能编辑代码；
- 即使授权实现，也应保持范围小，并解释改动原因、影响和验证方式；
- Codex 不读取 `.env`，不覆盖你未提交的修改，不调用付费模型做默认测试。

## 常用提问示例

理解代码：

```text
只分析，不修改代码。请解释 FunctionCallAgent 从收到 query 到产生 SSE 的完整调用链，并标出关键文件。
```

学习设计：

```text
我正在学习 Agent Queue 的设计。请先解释当前实现为什么只能支持单 API Worker，再给两个演进方案，不要实现。
```

定位问题：

```text
这个 Celery 任务偶尔重复执行。请结合当前代码找原因，区分已确认事实和推测，暂时不要改代码。
```

代码审查：

```text
请审查我未提交的 document_handler.py，只给问题、原因和建议，不要改文件。
```

请求小范围实现：

```text
请只修复你刚才指出的第 1 个问题，不要重构其他代码。完成后告诉我改了什么，并运行最小相关测试。
```

先学习再手写：

```text
不要直接给完整代码。先把这个功能拆成 4 个步骤，告诉我第一步应该修改哪个类、为什么，我写完后再请你审查。
```

## 提问时最好提供的信息

简单问题直接问即可。遇到 Bug 或设计任务时，补充以下内容会更高效：

- 你期望发生什么；
- 实际发生什么；
- 错误日志或复现步骤；
- 希望 Codex 只分析、给提示，还是直接实现；
- 哪些文件或行为不能改；
- 你已经尝试过什么。

不需要把这些信息写成复杂模板。对学习项目而言，明确“这次希望我自己写到什么程度”比长篇提示词更重要。

## 文档如何维护

- 稳定、长期有效的协作规则写入最近一级 `AGENTS.md`；
- 系统结构和调用链写入 `docs/architecture.md`；
- 启动、迁移和排障步骤写入 `docs/runbooks/`；
- SSE 等跨端格式写入 `docs/contracts/`；
- 某个多步骤流程反复出现且已经稳定后，再考虑做成 Skill；
- 前端开始开发后，再根据真实目录和工具添加 `llmops-web/AGENTS.md`。

当文档与代码不一致时，应先指出差异，以当前代码为准，并在你确认后只修改文档。
